# TZ Glasses: notes for Claude Code

Head-tracked AR navigation labels for Meta Ray-Ban Display glasses, fed by TimeZero Professional. Read README.md first for the overall setup.

## Status (handed over from a Claude chat session, 2026-11-23)

- `bridge/`: Python, tested end to end (UDP, serial, TimeZero database, GPX, WebSocket). Runs on the user's Windows 11 nav PC next to TimeZero Professional **v4**.
- `ios/`: written against the **real** Meta DAT SDK 1.1.0 interface files (`.swiftinterface` in the xcframeworks), following Meta's DisplayAccess sample. **Builds and runs in the iOS Simulator** (Xcode 27.2, 2026-11-24): demo data, simulated glasses, Connect, Motion and Gestures all work there. Not yet run on a real iPhone or real glasses.
- `ios/tests/test_head_math.py`: Python mirror of `HeadMath.swift`; passes. Keep the two in step if you change either.
- `android/`: Kotlin + Jetpack Compose port of the iOS app, written against Meta's Android DAT SDK 1.1.0 samples (DisplayAccess, BirdSpotter). `core/` (pure Kotlin: HeadMath, HudModel, BoatData/Json, DemoFeed) **compiles and passes `CoreChecks.kt`** (same head-math cases as the Python test, 20 seeds). The Android/Meta/Compose layers **have not been through Gradle yet** (Google Maven was blocked where it was written): sync in Android Studio and fix compile errors first.
- **Three implementations of HeadMath** (Swift, Kotlin, Python test). Change all three together.
- **Hardware: Meta Ray-Ban Display only.** Brilliant Labs Halo was considered and set aside (no gyroscope, so compass-only head tracking; 256 px drawable area).
- Customers are in **Atlantic Canada: Nova Scotia, New Brunswick, PEI and Newfoundland**. Demo and examples use Halifax Harbour.

## Meta SDK facts (verified from 1.1.0 interface files, not guessed)

- SPM: `https://github.com/meta/meta-wearables-dat-ios`, exact 1.1.0. Products: MWDATCore, MWDATDisplay, MWDATMotion, MWDATInputs, MWDATMockDevice.
- Install Meta's Claude Code plugin for live docs: `curl -sL https://raw.githubusercontent.com/facebook/meta-wearables-dat-ios/main/install-skills.sh | bash`, or connect the MCP server `https://mcp.developer.meta.com/wearables`.
- Display content is a single root `FlexBox` per `send()` (Text, Button, ButtonGroup, Image, Icon, VideoPlayer). There's no free drawing or absolute positioning, and text colour is only `.primary` / `.secondary`. That's why there are two lens modes:
  - `.picture`: the HUD drawn into a 600×600 `UIImage`, sent as `Image(image:)`. Full control; bigger transfer.
  - `.text`: FlexBox rows with flexible spacers to slide labels sideways.
  Which is better on real glasses is an open question: compare `lastSendMs` on device.
- Motion (`session.addMotion`) and Inputs (`session.addInputs`) are **experimental**. They must be enabled for the app in the Wearables Developer Center for production; Developer Mode may allow them. `MotionSample.orientation` is a quaternion with an **undocumented reference frame**. `HeadMath` detects the convention and sign at runtime, so don't hard-code an axis.
- Display and Motion need the `DeviceSession` in `.started` first; wait for `DisplayState.started` before sending.

## Data flow

`BridgeClient` (WebSocket JSON, see `BoatData.swift`) or `DemoFeed` → `AppModel.tick()` at 20 Hz → `HeadTracker.gaze()` → `HUDBuilder.build()` → `HUDImageRenderer` (phone preview and picture mode) → `GlassesController.send()`. Sends happen only when the frame changes or every 2 s, never overlapping, and capped by the "max updates per second" setting.

**Fixed heading (2026-11-25):** for a boat with no heading sensor and no course (tied up), Settings → Boat heading lets the user type in where the bow points. `AppModel.snapshot` fills `own.hdg` with it only while the bridge sends neither heading nor course, and the lens shows `HDG 345° SET`. Use `model.snapshot`, not `bridge.snapshot`, anywhere a heading is needed. Tested on the user's AIS demo PC (Icom MA-510TR via a hub4com split): 36 real AIS targets placed on the lens.

Gaze = boat heading at calibration + head turn since calibration + fine-tune. Using the heading at calibration (not live) is intentional: the glasses measure against the world, so labels stay put when the boat turns under a still head.

## Bridge facts

- TimeZero 4 output has no raw AIS (VDM). AIS arrives as **TTM** (target number, range, bearing, speed, course, CPA, TCPA, name), so there's no vessel type. TZ5 can export AIS, or the AIS receiver can be fed to the bridge directly.
- Marks and routes are read live, read-only, from `C:\ProgramData\TimeZero\DATA\UserObjects.tzdb` (SQLite). Geometry: 1 type byte, then big-endian int32 (x, y) pairs in **Web Mercator centimetres** (some marks have 4 extra bytes; ignored). Not degrees: it was first read as 2^31 = 180°, which looks plausible near Nova Scotia but is wrong and gets worse further north (a mark at 66°N read as 83°N). Fixed 2026-11-25, checked against a customer's file: as centimetres 78 of 84 marks lie within 1 nm of that boat's own Tracks2 track; as degrees 82 of 84 are over 10 nm off. Object type 0 = mark, 5 = route. Change detection: file times of the .tzdb and -wal **plus** a content fingerprint (`tz_signature`: counts, Deleted and LastModificationDate totals, ActiveRoute), because Windows may not update a file's time while TimeZero holds it open (the user saw Explorer's date stay put after adding a mark). Same for Tracks2.tzdb. Dates are seconds since 2000-01-01. Tracks live in `Tracks2.tzdb`: **decoded** (2026-11-24, from a real TimeZero 4 file) — format notes above `tz_track_points` in tz_bridge.py. Points are Web Mercator metres, delta-encoded and quantised per Portion; `MobileDescriptions.MobileType` 0 = this boat (others are logged AIS/ARPA targets, left out). The bridge finds it next to `--tzdb` and serves this boat's tracks within `--tz-track-range` (10 nm) in `/userdata.json` `tracks` (`source: "TimeZero"`), refreshed on file change or ~0.5 nm of movement. `Tracks.TrackOn` (2,532 of 7,041 set) might mean 'shown in TimeZero'; not used, unverified.
- **Getting NMEA out of TimeZero on the same PC:** TimeZero's UDP connection binds the same port it sends to (seen: TimeZero owning UDP 10110), so a UDP output to 127.0.0.1 on that port loops back to TimeZero and the bridge can't bind it. Use a TCP output (TimeZero as server, bridge `--tcp 127.0.0.1:PORT`; reconnects, and drops a connection silent for 20 s) or a virtual COM pair (com0com: TimeZero on one end, bridge `--serial` on the other).
- **Inputs:** `--serial`, `--udp` and `--tcp` repeat; each serial port takes its own speed (`COM11:4800`, `COM12:38400`, `COM12:auto` detects by trying common speeds for clean checksummed lines). Per-input line counts are in `stats.inputs` and on the status page. Duplicate values from two inputs: latest wins (no source priority yet).
- **NMEA 2000:** the user's boats have N2K and Actisense gateways. The bridge only reads 0183; today N2K comes in via TimeZero (reads NGT-1) or a gateway converting to 0183 (NGW-1, W2K-1). Decoding Actisense N2K directly (NGT-1 binary or W2K-1 raw ASCII: PGNs 129025/129026/129029 position, 127250 heading, 128267 depth, 130306 wind, 129038/129039/129794/129809 AIS) is not built; ask which gateway models first.
- TimeZero runs as administrator on the nav PC, so computer-use input into TimeZero is blocked; use the user's screenshots instead.

## Next: bring the demo's route, tracks and marks into the app

`hud-demo.html` is the reference for these. Perspective, marks, the route ribbon and tracks are **in the Swift app** (2026-11-24). None of it is in the Android port yet.

- **Perspective on the water (done in Swift).** `HUDBuilder.lensY` puts things below the horizon by the dip angle `atan(eyeHeight / range)`: `y = 0.5 + (dip + horizonDeg) / fovDeg` of the lens. Settings → On the water has eye height (default 3 m) and a horizon fine-tune. At real eye heights everything past ~0.5 nm hugs the horizon; only close things sit visibly lower. Labels sit above their marker and step up when they'd overlap, or drop below it when there's no room (edge-cue rows are kept clear). Still open: derive head pitch from `MotionSample.orientation` (HeadMath extracts yaw only).
- **Route as a ribbon (done in Swift).** `HUDBuilder.routeLayer` projects the ribbon into `HUDFrame.route` (lens-pixel quads, rounded, so equality still gates sends); `HUDImageRenderer.drawRoute` draws it under the labels. Active = the bridge sends `to_wp` and the next waypoint is found (`next_index`, else by name). Samples are never more than 0.04 nm apart so the rainbow shades smoothly; where the road is under 5 px thick (most of it, at real eye heights) it's drawn as a 5 px coloured line along the horizon. Animation steps at `routeAnimationFPS` (4/s); Settings → Route can turn the route or its animation off. The demo feed navigates the HTML demo's Harbour run (WP3–WP6). Original notes from the demo:
- **Route as a ribbon** (`drawRoute` in the demo): legs from the route's waypoints, ±16 m half-width, sampled more finely near the boat, each sample projected left and right edges → filled quads. Not active: thin dashed line. Active (TimeZero navigating it): legs from the boat onward become a **rainbow road** (hue = distance along route / 0.12 nm × 360 − time × 240, plus a faint wider glow and white edges). The part of the current leg behind the boat and earlier legs turn grey. Waypoints come from the bridge: live `route.waypoints` (RTE/WPL), else the active route read from `UserObjects.tzdb` (`active_route` in `/userdata.json` + `routes[].points`).
- **Tracks (done in Swift):** own track (amber, solid) and saved GPX tracks (blue, dotted), Picture mode only, drawn under the route. `BridgeClient` fetches `/userdata.json` when the state's `userdata_version` changes and every 30 s. `AppModel.recordOwnTrack` starts from the bridge's `own_track` (it keeps recording while the app is closed) and adds a point every ~10 m; a jump over 1 nm clears it. `HUDBuilder.trackLayer` projects points within `trackRangeNm` (default 6) with the shared `LensProjector` (the route uses it too). Settings → Tracks. TimeZero's own tracks now come from `Tracks2.tzdb` live (see Bridge facts); GPX still works too.
- **Marks (done in Swift):** `HUDFrame.marks`, drawn as violet icons on the water (fish, pots, danger, anchor, else a circle) with a one-line label, as their own layer so they don't compete with ship labels (up to `maxMarks` = 5, nearest first). `MarkIcon.classify` picks the symbol from GPX `symbol`, then `icon`, then the name's keywords. TimeZero's numeric `Icon` values go in `MarkIcon.timeZeroIcons` and win over the name (seen so far: 17 = skull → danger; the user is making one test mark per symbol and colour to map the rest). `Color` numbers aren't mapped yet (11 = orange); marks are drawn violet. Text mode shows marks as extra rows.
- **Danger-mark alarm (2026-11-25, Swift only):** `HUDBuilder.markThreats` flags danger marks (skull icon, or names like shoal/rock/wreck/danger) within `dangerMarkNm` (0.5) that are ahead and that the course over ground passes closer than `dangerPassNm` (0.1), or any within that pass distance when drifting. It uses the same banner as the collision alarm (`DANGER MARK 0.30 NM · 3 MIN`, name and side): a danger-CPA vessel outranks it, it outranks a caution vessel. The mark is drawn red, with a red edge cue when out of view; a tap acknowledges it for 2 minutes (key `mark:<TimeZero id>`). Settings → Danger marks. Planned next: boundaries as coloured walls (TimeZero object types 4/8 still unconfirmed; the user will draw a test boundary).
- **Text mode** can't draw lines (Meta's display components only), so the route and tracks are Picture mode only; marks appear as rows.
- **Picture mode bandwidth:** a moving rainbow means every frame changes. If Bluetooth can't keep up, animate the rainbow only every few frames or send a static rainbow.
- **Night looks (2026-11-26, Swift only, Picture lens mode):** Settings → Night picks `HUDSettings.lensLook` (Day / Night / Night red). Night draws everything except marks and alarms at 45% brightness (`HUDImageRenderer.nightDim`) and gives marks a glow (halo plus blur); Night red also multiplies the finished picture by pure red. With `lookAtSunset` on, `AppModel.look(at:)` uses Day while `Sun.isDown` is false at the boat's position (sun below -0.833°). Meta's kit has no lens brightness control, so dimming is done by drawing darker. Also in hud-demo.html (Day lens / Night lens / Night red, switching with the scene's time of day).

## Target sources (AIS / ARPA / online AIS)

- The bridge tags targets `source`: `"AIS"` (VDM, or TTM with acquisition `R` = reported), `"ARPA"` (TTM acquisition `A`/`M`, radar-tracked), or `"TTM"` (TTM without the field; treated as AIS). Unnamed ARPA targets are named `ARPA <number>`.
- **In the Swift app (2026-11-24):** sources `AIS`, `ARPA` and `ONLINE` (`HUDBuilder.sourceKey`; any `source` starting "ONLINE"). Each can be hidden and given its own label colour (Settings → Targets, `HUDSettings.sourceColors`, defaults as in the demo: AIS #8ff0c7, ARPA #ffb35c, online #7fc4ff). Online AIS shows its age from `age_s` ("4 MIN OLD") and is never used for collision alarms. **Bridge merge and online guess (2026-11-25):** with an AIS receiver also feeding the bridge directly (VDM), `BoatState._merged_targets` folds TimeZero's TTM copies of AIS ships into the receiver's targets (same name, or ≤0.15 nm and ≤2 kn apart); ARPA is never merged. A TTM AIS target still unmatched after 90 s, with the receiver heard in the last 60 s and running 90 s, is tagged `source: "ONLINE"` with no `age_s` (TimeZero gives none; the app shows "ONLINE"). Re-decided every snapshot. Tested with synthetic TTM/VDM only; not yet with the user's Icom MA-510TR. Without a direct receiver: TimeZero's UDP output wizard has no online-AIS option, so online targets may arrive as ordinary TTM with acquisition R and look like live AIS. Needs checking against real TZ5 output. How TZ5 outputs online AIS over NMEA is unknown: check with real TZ5 output before relying on it, and always show its age, because it can be minutes old and must not be treated like live AIS for collision alarms.

- **Testing online AIS:** run the bridge with `--record tz-test.nmea` on the nav PC while TimeZero shows online targets, then look for how they arrive (TTM acquisition field, names, VDM) and tag them `ONLINE` in the bridge if anything sets them apart.

## Chart buoys and beacons (lower priority, per the user)

The user wants charted aids to navigation (buoys, beacons, lights) on the lens, kept current as charts are updated. TimeZero's own chart files (C-MAP, S-63) are encrypted, so read chart data directly in the bridge instead:
- **S-57 ENC cells** (`.000` plus `.001`, `.002`… updates), e.g. with GDAL/OGR: layers BOYLAT, BOYCAR, BOYSPP, BOYSAW, BOYISD, BCNLAT, BCNCAR, BCNSPP, LIGHTS (OBJNAM, COLOUR, LITCHR, SIGPER). Watch the folder like the tzdb, so new update files apply automatically. Serve as `aton` targets (or a separate `charted` list) with a source tag `"CHART"`.
- Region is CHS (Canadian Hydrographic Service) waters. CHS sells ENCs as S-57 and S-63; only unencrypted S-57 can be read. Ask the user which charts they hold before building.
- Free fallback: OpenSeaMap seamarks (OSM `seamark:*` tags).
- Live AIS AtoN (message 21) already comes through as `kind: "aton"`; de-duplicate charted aids against those by position.

## Bridge installer (2026-11-25)

- The installed bridge is a Windows service (WinSW wrapping the PyInstaller folder build `tz-bridge.exe`), configured by `C:\ProgramData\TZ Glasses Bridge\config.json` and the `/settings` page (`/api/config` GET/POST; POST only from localhost, JSON only). Saving restarts the inputs in-process (`main_async` returns True, `main` loops).
- In config mode a busy UDP port is shown on the status page instead of exiting, so the service keeps running.
- Look (2026-11-26): `status.html` and `settings.html` share a dark-first nav-console style (light follows Windows), using only fonts Windows already has (Bahnschrift, Cascadia, Segoe), so nothing loads from the internet. The status page fetches `/api/config` for the phone address. Keep the text "TZ Bridge Settings" on the settings page: the installer test looks for it. Installer art in `bridge/installer/` (tz-bridge.ico, wizard-*.bmp, small-*.bmp, 24-bit bottom-up) was drawn by a throwaway Swift script; the mark is the same as the pages' SVG.
- **Virtual COM ports (2026-11-26):** the installer bundles com0com's signed 2.2.2.0 x64 `setup.exe` (CI downloads it from SourceForge with a `Wget` user agent: a browser one gets 403; if the download fails the installer builds without the `vcom` task) and runs it with `/S` (installs no pairs) when the task is ticked and com0com isn't already there. Then, whenever com0com is present, `trust-com0com.ps1` adds its driver signer (Steven William Hatchett, checked by name) to LocalMachine TrustedPublisher: the driver prompt appears when a pair is made, and the bridge service can't show it. The bridge drives `setupc.exe --silent` (`/api/vcom` GET list, POST add/remove, POST localhost only). It picks two free COM numbers itself (from 10 up, skipping Windows' COM Name Arbiter ComDB, SERIALCOMM, present ports and existing pairs; 2.2.2.0 may not support `COM#`) and sets `EmuBR=yes,EmuOverrun=yes` on both ends, as com0com's ReadMe advises against hangs. A serial input's optional `forward` (CLI `--pass-on COMx=COMy`) passes every line read on to another port through `PassOn` (own thread, 200-line queue, drops when the far end is stuck), replacing hub4com/VSPE. CI's "Test virtual COM ports" step runs the same setup and trust script, makes a pair via the API and sends a line through it; it's allowed to fail (the runner may refuse a kernel driver). Memory integrity (HVCI) on Windows 11 may block this 2011-signed driver. Not yet tried on the user's PCs. com0com is GPL v2: `com0com-NOTICE.txt` points to its source.
- `.github/workflows/bridge-installer.yml` builds and tests the installer on `windows-latest` (packaged replay, silent install, service running, settings round-trip, uninstall). Tags `bridge-v*` publish a release. Not code-signed yet (SmartScreen warning); add a signing step when there's a certificate.
